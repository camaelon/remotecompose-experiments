## 2. Dead ends / wasted calls (3)
- Call 8: missing `"profiles": 513`. The format reference mentions it in the header line, but not as required. A converter or kit default (or a build_kit skeleton) would have avoided it.
- Call 14: guessed the interact action shape. The `inspect` tool summary doesn't show it; one example in the tool description would avoid it.
- Calls 16-17: chasing a "continuous" verdict that is a 60-frame-window artefact of a 1.6 s ease at load. A verdict that says "animating, settles after N frames" would avoid it.
- (Half-dead: call 6. I read the Walkthrough definition and then decided not to use it, although build_kit and the design rule push it. Its pitfalls say autoplay stops on the last step, so I needed the definition to copy its techniques anyway.)

## 3. Wrong, misleading, noisy or missing tool output
- build_kit resolved "steps" to `use_case:fitness` and "stroke" to `capability:draw.stroke` (twice). That is noise: here "stroke" is the engine stroke. It also suggested icons "valve" and "animation" for this goal, which don't help.
- build_kit's single layout example is TIM-14 (a stopwatch) "Structure the screen like this". It is irrelevant to an explainer with a drawing.
- The Walkthrough design rule ("Use the Walkthrough component for the frame") doesn't say that autoplay can't loop. A cyclic process (engine, heart, water cycle) wants a loop, and the component has no `loop` option.
- `inspect runtime` / `audit` default window: "verdict": "continuous" and audit info `repaint_continuous` for a document that is idle once a 1.6 s load ease ends. Misleading for the "does not repaint when paused" check. Only `frames: 240` showed `idle`. Also, why does an animated value whose target never changed animate for 1.6 s at load?
- The components guide says "`animationTime()` alone never schedules a repaint; use `continuousSec()` for motion", while the Walkthrough pitfalls say a continuousSec() clock "would keep the document repainting even while paused" and use the animated-local trick instead. The guide's advice is the wrong one for paused/idle documents.
- render `animation_time`: "Ignored when simulating", and `variables`/`samples` always simulate ("the state one second in"). So pinning a mid-stroke frame needs indirect tricks (I shifted t0). A `samples` entry with `$animation_time` would help.
- Steps (library) clips its own label ("Compression") at 288 dp wide (render's text_overflow warning). The component gives no option for shorter labels or wrapping.
- interact output lists dozens of anonymous derived expressions (`"name": null`, `(24 + var_130)` ...) for one tap sequence. Noisy. The named state was what mattered.

## 4. What I would have liked
- A Walkthrough `loop: true` (autoplay wraps to the first step) and a per-step "progress" output (0..1 within the step) for in-step animation. That is exactly what I had to build myself.
- A way to have one layout that is a column on a phone and a row on a tablet without writing the subtree twice (the stateLayout doubles the drawing's bytes).
- `inspect runtime` reporting "settles after N frames" rather than a verdict over an arbitrary 1 s window.
- An example of a mechanical/kinematic drawing (crank-slider) in the catalog.
- A live-region / announce-on-change semantic, so a step change is announced without focus moving. The tools never mention whether the visible title's description is announced when it changes.

## 5. Honest assessment
- **Correctness**: the crank-slider kinematics are real (r 28, rod 80, sin/cos with the rod angle). Valve timing: intake open in intake and closing early in compression; exhaust open in exhaust with overlap into early intake. The spark fires for the first 30% of the power stroke. The crank turns half a revolution per stroke, continuously across steps. While paused, each step rests at the END of its stroke (BDC/TDC), so the paused power step shows no spark; the spark is visible only in the stroke animation or while playing.
- **Interaction**: Prev/Next wrap around (exhaust -> intake) and play the stroke once (1.6 s ease of a tap counter). Play runs the cycle continuously (2.5 s per stroke) and the caption and indicator follow. Pause keeps the step on screen. A tap on Prev/Next while playing stops play. Pausing makes the piston jump to the end of the current stroke (weak spot).
- **Repaint**: idle when paused (after the 1.6 s load ease); continuous only while playing.
- **Themes**: light and dark use theme colours only. In mono the gas washes are removed and the gases differ by shape (dots / asterisks / rings) and by a label beside the cylinder. Mono has no play button and no motion (as the guide prescribes), so mono shows the end-of-stroke poses only.
- **Sizes**: phone 400x820 good. Narrow 288 clips "Compression" in the Steps labels. Landscape tablet is side by side. Portrait tablet uses the stacked layout (a deliberate choice; side by side wasted half the screen).
- **Accessibility**: the document description is set; the drawing has a contentDescription naming parts and gas shapes; the title is announced "Step N of 4: X stroke" followed by the explanation text; the buttons are labelled "Previous stroke", "Play"/"Pause" and "Next stroke", with 48/56 dp targets. Not verified: announcement of the change itself (no live region).
- **Bytes**: 25.8 KB, mostly expressions. The drawing is duplicated for the two layouts. The asterisk/dot loops are cheap.
- **Weak spots**: the end-of-stroke rest pose; the jump on pause; the drawing's labels are canvas text (fixed relative size, not font-scaled); the Steps "done" ticks imply a linear progression for what is really a cycle.
