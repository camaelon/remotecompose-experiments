# Eval 56, run 1: time-zone meeting planner

Final document: `planner.json` (generated by `src/gen.py`) -> `planner.rc` (19,085 B), playground `planner.html`.
22 CLI calls (counting `list` and two `describe`), 0 hard dead ends, about 3 partly wasted calls.

## 1. Tool calls in order

1. `list`: what servers and tools exist. Learned the 5-step workflow and that `remotecompose` combines the other servers. Decided to start with build_kit.
2. `build_kit` (the goal, verbatim): it resolved Slider and WorldMap, gave MAP-01, MAP-02 and TIM-13, and design rules. Learned that WorldMap's geometry is static (only one host marker), and that a Slider value has to be read after the slider. Decided to draw my own canvas with `$map` so I could add a moving working-hours band and 5 host-driven markers.
3. `describe reference`: to see the topics and the `query` option.
4. `reference` query "map mapPoint mapHeight canvas overlay longitude band": got the `$map`/`$mapHeight`/`$mapPoint` paragraph (a box 1000 wide, equirectangular). This came back twice, as a duplicate paragraph.
5. `reference topic=format`: layout, visibility (needs a declared 0/1 variable), textFromFloat flags, host strings as root `variable` commands, arrays, system_variables `{"10": ...}` for offsetToUtc. This was the most useful call.
6. `get CMP-03` (json, meta): checked how a Slider is bound and read. A value read after the slider is live. Expressions in resources keep the starting value.
7. `reference` query "expression computed from slider value after the slider…": tried to find how to derive live values after the slider. The answer was not useful (pattern-mode tables). This call was partly wasted.
8. `reference topic=components`: the authoring guide (params, locals, `$if theme.mono`, mono rules). Decided on two inline components: CityRow and WorkHoursMap.
9. `reference topic=expressions`: step(x, edge) is x > edge, % keeps the sign, round/floor exist, and resources cannot read tree variables. Decided to bind the slider and use onRelease, so the resource expressions update when the finger lifts.
10. `convert` check: true. It was ok on the first try (17.7 KB) and reported the host variables.
11. `render` light, user at UTC+1: first look. The layout and the map band were right. The offsets printed as "UTC+1.0", which was ugly.
12. `describe render`: to learn samples, sheet and variants.
13. `render` samples hour 0 / 7.25 / 9.6 / 13 / 18.4 / 23.75, user UTC−7, sheet: every city's time, status, day shift and band was correct at each value. The 9.6 value snapped to 09:30.
14. `render` variants, sheet, user UTC+5:30: dark, light and the two monos looked right. In narrow (288) the city names were clipped. In mono-light, the black dots on the dark-grey band were hard to see. Decided to move the status under the time, let names take 2 lines, and draw the band in mono as edge lines plus a top bar.
15. `render` mono-light at 288 and 400 sizes: the fixes worked. Nothing was clipped.
16. `render` with touch_events (a drag from 16:30 to x=100): after release the time read 05:00 and the map, cities and day shifts all followed.
17. `audit`: 0 errors and 0 warnings. One info said the library Slider's 40 dp touch target is under 48 dp.
18. `inspect accessibility`: the slider announces its label with state "16", the raw hour, not 16:30. Offsets are read as two fragments ("UTC−", "7:00"). Each city's time has a description. Decided to add a description to each status pill ("Tokyo is at night").
19. `convert` final: ok, 19,085 B.
20. `render` with the user in Tokyo (UTC+9), plus a sample where the host replaces city4 with Sydney and changes the offset, lon and lat arrays: everything was correct, including "−1 day" for the US cities.
21. `inspect bytes`: the world land path is 5.7 KB (30%), expressions 3.3 KB and text 4.7 KB.
22. `publish` with output_path planner.html and variable_ranges hour: a 736 KB playground.

## 2. Dead ends and wasted calls
- Call 7 (reference query) answered with pattern-mode tables, not how to compute live derived values after a slider. A short "derived values from a slider" recipe in the Slider pitfalls would have avoided it.
- Call 3 (`describe reference`) only existed because `list` truncates descriptions. I could have guessed `query`.
- Call 18 output is large JSON. I had to run a local script to read it, though this is not a tool call.
- There were no real dead ends: the first convert was valid and the first render was correct.

## 3. Wrong, misleading, noisy or missing in tool output
- There is a contradiction about the Slider. The Slider `value` doc says "@volume read after the slider is the live value". The format topic says "A library Slider writes its bound variable when the drag ENDS (onRelease), so a preview computed from it updates on release". Both are partly true, but nothing explains how to get a live derived value. Resources "never [read] a 'variable' command declared in the tree", and visibility needs a declared variable. So a computed status cannot follow the drag live. My app updates on release.
- CMP-03 says "textFromFloat drops trailing zeros". With decimal 2 and flags 5, 1 printed as "1.0". I worked around it with H:MM.
- The WorldMap doc and format say "a world at low detail is ~3.5 KB". `$map` world land at low detail measured 5,681 B.
- In build_kit, the Slider's `label` doc says "A screen reader hears the label and the current value". The value it hears is `textFromFloat` with `decimals` digits, so an hour slider says "16" for 16:30. There is no param for a custom state text such as a formatted time.
- The audit flags the library Slider (40 dp tall) as under the 48 dp touch target. The library component trips its own audit.
- The variants render warns that "at 288×860 the content no longer fits" and recommends collapsibleColumn/fitBox for a widget. This is noise for a scrolling phone screen that already has verticalScroll. The real problem, the clipped names, was reported correctly as text_overflow.
- The `reference` query returned the same Maps paragraph twice (call 4).
- build_kit offered TIM-13 (tides) as the layout model. It is long and unrelated (35% of the output). No example combines a slider with derived per-row status.
- `$if` without `else` in a canvas command list is not documented. It worked.
- In the render result, "click miss" on the slider's up event reads like an error. It means only that no onClick was there; the drag worked.

## 4. What I would have liked
- A Slider `step` (e.g. 0.25) and a `stateText` param (a text object) so a screen reader hears "16:30".
- A documented pattern for "derived values follow a slider live" (a canvas global block? a tree variable?).
- WorldMap options for a longitude band or time-zone shading, or a recipe in the Maps paragraph (x = (lon+180)/360*1000, y = (84 - lat)/142*mh for "world"). I worked these out myself from "latitudes 84 to -58" in the night pitfall.
- Real time-zone polygons (shading by zone) instead of solar-longitude bands.
- `samples` able to set system variables (offsetToUtc) per sample, so one sheet can compare user time zones.
- `inspect accessibility` as a compact text reading order.

## 5. Honest assessment
- **Correctness:** I checked by hand at hours 0, 7.25, 9.6, 13, 16.5, 18.4 and 23.75, and with the user at UTC−7, UTC+1, UTC+5:30 and UTC+9. City local times, the ±1 day markers, the status (Early 06–09, Working 09–18, Late 18–22, Night) and the band were all correct. The slider snaps to 15 minutes (round(@hour*4)/4, max 23:45).
- **Map choice:** the shading is a longitude band of local *solar* time (09–18 = 135° wide, wrapping), not real time zones, and the legend says so. Cities are coloured by their real offset, so a city near a band edge can disagree with the band. For example, at 16:30 UTC San Francisco (UTC−7, 09:30) is filled but sits just west of the band. This is a known weak spot.
- **Host variables:** city0..city4 are strings. cityOff, cityLon and cityLat are exported float arrays (the app keeps DST right). `hour` is exported, and the onRelease sends `setMeetingHour`. The user's zone comes from offsetToUtc().
- **Sizes:** the phone is 400×860. It also works at 288 wide, on a tablet and wide (verticalScroll). It is not meant as a widget.
- **Themes and mono:** themed colours are used throughout. In mono, the band is edge lines plus a top bar, the land is an outline and the working pill is a filled face. The legend wording "Shaded" is slightly off in mono.
- **Repaint:** idle except when offsetToUtc changes. The document reads no clock (the meeting time is chosen, not now).
- **Accessibility:** there is a document description and a map description. The big time reads "Meeting at 16:30 your time, 15:30 UTC". Each city reads "<city> local time HH:MM" and "<city> is in working hours / early / late / at night". The slider's own state is the raw hour ("16"), which is a library limitation. Offsets are read in two fragments.
- **Bytes:** 19 KB. The map path is 5.7 KB, and 5 expanded CityRows make up most of the rest.
- **Weak spots:** values update on release, not during the drag. The axis labels under the slider are spaced, not aligned to the thumb's exact track. There are no city labels on the map; only the dots and the list below identify them.
