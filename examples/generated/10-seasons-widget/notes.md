# Seasons widget: evaluation notes (prompt 10, run 2)

Final document: `seasons.json` (generated by `gen.py` + `gen2.py`), `seasons.rc` (23,612 B).
Render sheets: `img/32-render-final-clocks.png` (transition dates), `img/33-render-final-variants.png` (themes, mono, sizes),
`img/sheet-tz-south.png` (time zones plus southern hemisphere), `img/sheet-thresholds.png`, `img/sheet-small.png` (layout switch points).

## Assumptions
- Astronomical seasons (they start at the equinox or solstice), not meteorological ones (1 Mar, 1 Jun, ...).
- Hemisphere: northern by default; an exported host variable `south` (0/1) shifts the season by two. The events are named by month
  ("March equinox", "December solstice"), so the names hold in both hemispheres.
- Event instants: Meeus' mean equinox/solstice JDE0 polynomials (years 2000-3000), linear term only, turned into epoch days:
  March 11036.30984 + 365.24237 n, June 11129.06767 + 365.24163 n, September 11222.71715 + 365.24202 n,
  December 11312.55952 + 365.24274 n (n = year - 2000; UTC; I ignore TT-UT). The periodic terms are left out, so the error is
  roughly ±15 min (2026: March 14:40 vs the real 14:46, June 08:24 vs 08:24, September 00:14 vs 00:05, December 20:54 vs 20:50 UTC).
  Converted to the local date with the device's current offsetToUtc(); I ignore a DST change between today and the event
  (that is off by one day only when the event falls within an hour of local midnight).
- On the day of an event the new season shows and the event reads "Today" ("March equinox is today"). The day count is in whole
  local calendar days.

## 1. Tool calls (34 in total, all `remotecompose`)
1. `list`: to get the workflow and tools. Used the 5-step workflow (build_kit, then components, then assemble, convert/render/audit, then publish).
2. `build_kit` (the verbatim goal): got DateLabel, TIM-12 (sunrise maths), TIM-08 (layout model), design rules, and
   `not_covered: calendar arithmetic` pointing at `reference expressions`. Decided to compute the event dates in the document as epoch days.
3. `reference topic=expressions`: the calendar-arithmetic recipes (leap, today's epoch day, month from day of year, eq()) and the
   32-entry limit. This was the most useful call. I took the epoch-day formula and the step/ifElse rules.
4. `get TIM-08 parts=json`: the document skeleton (header, resources.variables, column/text syntax).
5. `find kind=components`: found ProgressRing and Icon (TextChoice was not listed for my query). Decided on a ring showing
   season progress with a season icon in the middle.
6. `get TextChoice`: its params and pitfalls (index rounded and clamped, about 90 B per item, the visibility trick).
7. `get Icon`: params (size static, label).
8. `find kind=icons` "snowflake flower sun leaf": picked local_florist, sunny, eco, ac_unit.
9. `reference query=visibility...`: visibility needs a declared 0/1 variable, a call needs a wrapping box, there is no
   contentAlignment, semantics syntax, and weighted children ignore spacedBy (so I fixed the spacing before the first convert).

11. `convert json=<inline>, check:true`: ok, 13,395 B, no findings.

    see below). The "Today" state needed work.
14. `render variants:true`: themes and mono were fine, but narrow, 2x2, 4x1 and tiny sizes clipped badly; the size warning named collapsibleColumn/fitBox.
15. `reference query=fitBox`: told me fitBox picks by minimum content width, which is unreliable with texts, so use a stateLayout on
    windowWidth/Height. Chose a stateLayout.
16. `reference query=inline component...`: the component definition syntax (params, body, call).

## 2. Dead ends and wasted calls (2, plus a few re-renders)
- Calls 10 and 12: I gave file paths in my own folder (json_path, output_path). The tools only accept paths inside the server
  workspace, and I only learned that from the error. The descriptions say "Paths are relative to the server's workspace",
  but nothing says what or where that workspace is, and the brief told me to write into my folder. If `list` or the
  error had said "pass json inline, images land in out/ under <root>", both calls would have been avoided.
- Calls 24 to 28 (5 renders) went into getting the size thresholds right by trial. A tool that reported each layout's minimum
  size (or the stateLayout index picked at each variant size) would have cut this to 1 or 2 calls.

## 3. Wrong, misleading, noisy or missing in the tools' output
- build_kit led with DateLabel ("Today's date from the host clock"), but the widget needs the date of a *computed* future event,
  which DateLabel cannot show. It was noise for this goal. The relevant part was buried in `not_covered`
  ("calendar arithmetic: no example, but recipes in reference expressions").
- build_kit `icons.suggestions` came back empty although the goal names seasons (snow, flower, sun, leaf are obvious).
- TIM-12 (sunrise) was offered as "the goal's subject: season, season, solstice, equinox, day". It has no equinox/solstice
  computation, and its 16 KB is not a usable starting point. No example computes solstice/equinox dates, and I had to bring the
  Meeus constants myself. The design rule says "don't state precise data (event times) you cannot compute or source", but
  nothing helps you source them.
- `find kind=components` with "progress ring text choice icon season" did not return TextChoice (it returned Avatar, Rating,
  BatteryIndicator...), although build_kit's design rules recommend TextChoice.
- The variants render's size warning recommends "a collapsibleColumn ... or switch to a compact layout with a fitBox", while
  `reference` on fitBox then says that with texts the fitBox picks unreliably and to use a stateLayout instead. The render
  warning should point at the stateLayout option first for text-heavy alternatives.
- The size warning at 259x180 in call 24 ("the content no longer fits") was printed with no named variant; the detail came lower down.
- Path errors: "is outside the workspace" without saying which directory the workspace is.
- The `render` tool notes say images are "relative to the server's workspace", and the output says `out/render-...png`. That
  turned out to be relative to the repository root. Fine, but undocumented.
- No way to group a widget into one accessibility announcement (no merge-descendants semantics found), so the screen reader hears
  "51", "days until the", "December solstice", "Mon ", "21", " December ", "2026" as separate nodes.

## 4. What I would have liked
- An astronomy/calendar recipe or component for equinoxes and solstices (dates from the year, like the sunrise maths in TIM-12),
  or at least a pointer to sourcing them.
- The render result reporting which stateLayout child was shown at each size, and inspect giving each alternative's minimum size.
- A way to write text output to a folder of my choosing (or a clear statement of the workspace root).
- An EventDate-style library component: format a computed epoch day (not just today) with weekday and month names, with a full-word
  accessibility label like DateLabel has.
- Semantics merge (one contentDescription for a group made from textMerge of several live texts).

## 5. Honest assessment
- **Correctness:** the season, the next event, its date (with weekday) and the day count are right on every pinned date I tried:
  the days either side of all four 2026 events, the midnight edges, 31 Dec / 1 Jan, 29 Feb 2028, UTC-7 and UTC+13, and both
  hemispheres. Everything is computed from the clock (no pasted dates), and it should hold for decades. Known limits: ±15 min
  event accuracy (a wrong date only when an event falls within about 15 min of local midnight), the current UTC offset is
  applied to a future event (DST), and it assumes astronomical seasons.
- **Small sizes:** five layouts chosen by a stateLayout on the window size. Full (≥300x130): ring, season, big count,
  "days until the", event, date. Wide-short (≥240x76): compact row. Narrow-tall (≥150 high): stacked column. Small: ring,
  season and count. Tiny: ring and count. No clipping findings from 80x50 to 576x135. The two smallest drop the date and event
  name, and the 2x2 text is 11 sp, which is small.
- **Themes and mono:** only theme colours. Light, dark, mono-dark and mono-light all render cleanly. In mono the ring track is a thin outline.
- **Accessibility:** a document description, a live label on the ring ("N percent of the season has passed"), and a live label on the
  tiny layout. The texts are readable layout texts, but split into fragments; the abbreviated weekday is read as "Mon".
  Text sizes are fixed sp numbers, and the stateLayout thresholds do not account for a large font scale.
- **Bytes:** 23.6 KB, which is large for a widget: 4 icon paths (about 3 KB), five layout copies, and many TextChoice items
  (about 90 B each). Dropping a layout or the weekday would save several KB.
- **Weak spots:** "Today" shows an empty ring with a dot (the new season is at 0 %). Below 240 wide, the date and event name
  disappear. The southern hemisphere needs the host to set `south`; there is no latitude detection. The English strings are hard-coded.
