# Server status dashboard: eval notes (prompt 25, run 1)

The deliverables are `doc.json`, generated by `gen.mjs` (the six rows and the summary come from one component definition each, so nothing is pasted six times), and `doc.rc`, which is 44,530 B. `server-status.html` is the playground page from publish. Renders are in `out/`, and the tools' outputs are saved as *.txt.

Host variables, one set per service i = 1..6:
- `name1..6`: a string, the host name.
- `st1..6`: a float, 0 = up, 1 = degraded, 2 = down.
- `lat1..6`: a float, the latency in ms.
- `up1..6`: a float, the uptime in %.

## 1. Tool calls, in order (30)
1. `list`: server overview. I took the 5-step workflow from it (build_kit → components → assemble → convert/render/audit → publish).
2. `build_kit` (the goal verbatim): Icon, the CMP-08 layout model, the EXP-10 and EXP-04 techniques and the design rules. `needs_component` was empty. I decided to build from Icon + ProgressBar + TextChoice + my own inline components.
3. `reference format`: the JSON essentials. I took host strings (root `variable` commands), exported floats, textMerge/textFromFloat flags, visibility on declared variables, fitBox, stateLayout and the widget sizes from it.
4. `reference components`: the authoring guide. I took locals, `$if`, params, mono rules ("show state by shape") and "no colour expressions" (so colours are switched by overlaid copies) from it.
5. `get ProgressBar`: its params (progress, color, height) and the fact that it fills its parent. I used it for the latency and uptime bars.
6. `find icons` "status ok error warning": I picked `check_circle`, `warning` and `cancel`, all filled, so each status has its own shape in mono.
7. `check_component StatusIcon`, swept over status 0/1/2: correct in light, dark and mono, 627 B per extra instance.
8. `describe render`: I learned the `variants`, `samples` and `componentTheme` options.
9. `convert check:true`: OK at 29 KB. It reported "content ends at 60%", which led me to find that the fitBox had picked the compact layout on a phone.
10. `render variants` (v1): the fitBox showed NOTHING at narrow sizes, and the full layout "needs 364" wide even at 360. I switched to a stateLayout keyed on windowHeight().
11. `render variants` (v2): host names were cut to "api.exam…" by the two fixed 84 dp columns. I redesigned each row on two lines.
12. `get TextChoice`: its fontSize, color and maxLines params, used for the status word.
13. `render variants` (v3): the rows look good. The render reported a false `text_only` suggestion (see section 3).
14. `render 320x160`: the compact 2×3 grid is right.
15. `render 250x110` (dark): the cells were too short and the icons clipped. I tightened the padding and the icon size.
16. `render 800x1280` (tablet, with a separate 2-column layout): it looked fine but the document was **61 KB**. I replaced the duplicate layout with a `flow` and a computed item width.
17. `render 800x1280`: the flow gives 2 columns on the tablet at 33 KB.
18. `render variants` (v4): all clean except the "tiny" 180-wide size (clipped labels). I added ellipsis to the labels.
19. `render samples` (4 sets: all up; one down; two degraded at 640/880 ms; 4250 ms with 87.5 % next to 99.99 %): the summary, icons, bars and colours are all correct.
20. `inspect accessibility`: each row read "name, latency…, uptime…" but **without the status**. I moved the full sentence onto the visible status icon's label instead.
21. `inspect accessibility`: each row now reads "db-primary.internal is degraded. Latency 342 milliseconds, uptime 99.2 percent". The header reads "4 of 6 up, 1 degraded · 1 down" plus "A service is down".
22. `audit`: only info-level deep nesting (×102). Nothing actionable.
23. `inspect bytes`: 35 KB. The largest parts were FloatExpression (238 ops, from the ProgressBar animated locals) and TextMerge (266 ops).
24. `render 320x160` light: the widget cells show numbers only. That does not meet the "small visual" requirement, so I added two 3 dp mini bars per cell.
25. `render 250x110` mono: it reads well, with the status shapes distinct.
26. `render 320x160` light: the mini bars are in, but tight.
27. `render variants` at 320x160: every finding was "none", yet the 4x1 (320×80) image is an illegible smear (see section 3). I added a third layout: the header plus a strip of 6 status icons.
28. `render 320x80`: the strip layout is right.
29. `convert check:true`: final document, 44,530 B, parses fine.
30. `publish` → `server-status.html` (1.19 MB playground). It lists all 24 host variables.

## 2. Dead ends and wasted calls
- **fitBox for phone versus widget (calls 9–10).** I followed build_kit's "switch to a compact layout with a fitBox… list the full layout first". A row with an ellipsized name inside a weighted column still counted the name's full one-line width, so the full layout "needed 364" and never fitted at 360. What would have avoided it: build_kit telling me that for a list-vs-grid switch, a stateLayout on windowHeight() is safer. The reference mentions a window-driven stateLayout only for "round or square vs wide".
- **Fixed-width metric columns (call 11).** Two 84 dp columns left about 60 dp for the host name. This was my own design error, but no example in the kit showed a list row of the "name + two metrics" kind.
- **A separate tablet layout (calls 15–16).** Four alternative layouts each expanded every component, which made the document 61 KB. Nothing warned me before I measured. `flow` with a computed item width did the same job for half the bytes.
- **The first accessibility pass (call 20).** I put a row-level contentDescription built with textMerge, but the status word could not be merged into it: TextChoice is a layout component, not a text value, and the TIM-11 canvas-global trick is heavy. Putting the sentence on each state's icon label works, and I found that by trial.
- **4x1 (calls 27–28).** This size was not requested. Adding it after variants showed a broken render cost two calls and about 5.5 KB.

So 4 real dead ends (fitBox, fixed columns, duplicate tablet layout, accessibility without status) and about 6 calls spent on them.

## 3. Wrong, misleading, noisy or missing tool output
- **False design blocker.** render reported: `NOT DONE YET: this document has design problems to fix before it is shown or published. - [text_only] A screen of 8 texts and nothing else. No icon, drawing, chart or image`. The document at that point had 7 icons and 12 progress bars. It appeared on calls 13–16 and then disappeared after unrelated changes. A new user would be sent chasing a problem that does not exist.
- **Variants miss a broken render.** At 320×160, `── widget 4x1 320×80 → … findings: none` and `short 320×96 … findings: none`, yet the 4x1 image was a squashed smear of clipped cells. The checks for overflow and clipping did not catch rows squeezed into a few pixels.
- **The variant set depends on the base size.** Rendering variants at 360×640 never produced a 4x2 or 4x1 size; "short 360×384" is labelled "(a widget resized down)" but is not a widget size. I had to render 320×160 myself to discover the widget path.
- **fitBox guidance is incomplete.** The fitBox_no_fit message ("Make the last child fit the smallest size you support") is accurate. But the advice to put text in "maxLines + overflow ellipsis" did not lower the row's minimum when the text sits in a weighted column. The full layout still "needs 364x440".
- **build_kit relevance.** `unmatched_terms: server, service, up, latency, uptime` meant the core of the request matched nothing. The icon suggestion for "service" was `design_services`, which is irrelevant. EXP-04 is a canvas demo. Nothing in the kit was about a list of items with a status. It gave no hint for a host-supplied enum status, nor for counting states across items ("5 of 6 up"), which I had to write myself as per-item flags summed.
- **Noise.** check_component left 5 extra `render-*.png` files in out/ besides its 5 announced images. convert's `unused_space` info ("add what the screen is for") fires on a scrolling phone list and a tablet dashboard, where empty space below a list is normal.
- **Default theme.** A render without `theme` came out dark (320×160, 800×1280). Nothing says that is the default.
- **Accessibility bounds look offset.** The first card is reported at `x: 24, w: 336` inside a screen whose cards are drawn at x 12. That is x + w = 360 with 12 dp padding, so it looks like the padding is counted twice. I am not certain.
- **No warning about size.** No tool says that 44 KB is large for a widget, or that every alternative layout re-expands every component. inspect bytes shows TextMerge ×266 and FloatExpression ×238 but does not attribute them to components (ProgressBar's animated local, my labels).
- **Mono loses colour-only states and nothing flags it.** The slow-latency bar (red) and poor-uptime bar (amber) look the same as the normal bars in mono. The guide says "show state by shape" but no check flagged it.

## 4. What I would have liked
- A kit entry for a "status list": a row with an icon, a name and metrics, plus a summary count over host enums.
- A text-value form of TextChoice (textLookup usable in a layout textMerge), so one row-level contentDescription can include the status word.
- Variants that always include the widget sizes (4x2, 4x1) whatever the base size.
- A size budget warning, plus bytes per component call in `inspect bytes`.
- A mono check that flags states differing only by colour.
- A note on which wins for whole-layout switching (fitBox, stateLayout or collapsibleColumn), with the width-minimum caveat up front.

## 5. Final screen: honest assessment
- **Phone (360×640):** a header with an overall status icon (check / triangle / cross), "4 of 6 up" (computed from `st1..6`) and "1 degraded · 1 down". Below it are six cards, each with:
  - line one: the status icon (green check / amber triangle / red cross), the host name with ellipsis, and the status word (TextChoice);
  - line two: Latency (value plus a bar on a 0–1000 ms scale, red above 1000 ms) and Uptime (value plus a bar on a 90–100 % scale, amber below 99 %).

  The list scrolls when short and fits at 259 wide. At 180 wide it is cramped but the labels ellipsize.
- **Tablet (800×1280):** the same cards in two columns through flow (width ≥ 600). There is a lot of empty space below them, which is the weak spot here.
- **4x2 widget (320×160, down to 250×110):** a one-line header plus a 2×3 grid of cells. Each cell has the icon, the name and "84 ms · 99.99 %". At height ≥ 140 there are also two 3 dp mini bars, which do not change colour. Below 140 only the icon and name are left. It is tight: the bars sit near the cell's bottom edge.
- **4x1 (height < 100):** the header plus six status icons.
- **Themes:** light and dark use theme colours throughout. Mono and mono-inverted read by icon shape, but slow latency and poor uptime differ only in bar length there (colour lost).
- **Accessibility:** document description; the header gives the summary sentence; each service icon carries "<host> is <status>. Latency N milliseconds, uptime P percent". The visible texts are also read individually, which is redundant. The 4x1 icons only say "Up/Degraded/Down", without names.
- **Sample checks:** all up, one down, two degraded, 4250 ms and 87.5 % next to 99.99 % all render correctly. The summary counts treat "up" as status 0 only, so degraded services are not counted as up; that was my choice.
- **Bytes:** 44.5 KB (`auto` theme). That is large for a widget. The causes are three alternative layouts, 6 rows + 6 cells + 6 strip icons, about 30 animated ProgressBars and the label merges.
- **Known weak spots:**
  - status is a float enum: an app sending 0.5 would show "Degraded";
  - the uptime scale (90–100 %) is not labelled on screen;
  - the latency scale is linear and capped at 1 s;
  - the widget cells are tight;
  - the tablet has a lot of empty space;
  - ProgressBar animation is wasted on a widget.
