# Fitness dashboard — eval notes (prompt 36, run 1)

Deliverables: `fitness.json` (source, generated by `gen.py`), `fitness.rc` (32,570 B), `fitness.html` (local playground),
renders in `out/` (`final-*.png`, `samples-sheet.png`, `mono-sheet.png`, `final-sheet*.png`).

## 1. Tool calls (26 total)

1. `list`: read the workflow and tools. Took the steps (build_kit, then convert/render/audit). Decided to follow them literally.
2. `build_kit` (goal verbatim): got LineChart, Icon, TIM-13 (tides) as layout model and STR-11 (heart-rate sparkline drawn on a canvas). "calorie" was unmatched. There was no `needs_component`, and nothing for progress against a goal (ProgressRing/ProgressBar). Decided to use LineChart for the hour, ProgressRing for the goals, and TIM-13's structure.
3. `get TIM-13 json`: looked at how host data is exported (`floatArrays {value, export}`), at the Panel component (the mono outline), and at visibility switching. Copied Panel.
4. `get ProgressRing`: params (progress, color, size, thickness, showLabel). It has no a11y `label` param, so I put semantics on the tile row instead.
5. `reference format`: host numbers go in `resources.variables {value, export}`, semantics is a modifier and can take textMerge, `stateLayout` switches on the window size, and there are traps (spacedBy with weights, visibility needs a declared var). Very useful.
6. `convert check`: OK, 21,970 B, with a warning that the phone tiles overflow by 12 px.
7. `render variants` (v1): phone, widget, tablet, mono. Found the zone meter's current segment faint (step strictness, see 12), the tiles cut, and short heights squeezing the chart.
8. `render variants` (v2): after moving the alpha to declared vars and stacking the tiles. The short 360×384 height squeezed the chart to a sliver and the 4x2 widget's bottom row was cut. Decided on a 4-state stateLayout: widget, short phone, phone, tablet.
9. `render variants` (v3): only "narrow" still overflowed by 12 px. Root cause: `spacedBy` in a row with a weighted child. The reference warns about exactly this and I missed it.
10. `render samples` (light; hr 58 flat hour, 150 spiky, 185 peak, goals exceeded): zones and the "Goal reached" text were right. In the flat hour, LineChart `extremes` drew a dot on every sample, so the line looked like a thick bar.
11. `render samples` (mono-inverted, 320×160): zones were readable from the name and the number of filled segments. The flat hour gave a huge blob in the widget.
12. `reference expressions`: learned that `step(x, edge)` is 1 when x > edge (STRICT). This explained the v1 meter and the "goal exactly met" edge. Moved the thresholds to 99.5/129.5/159.5 and goal − 0.5, and added `varied`/`flat` vars to switch between a chart with extremes and one without.
13. `render samples`: **wasted**. Every sample failed because `hMax` was declared after `varied`. The error message was good ("declared AFTER an expression that reads it").
14. `render mono samples`: **wasted**, same error (it was already queued in the same command).
15. `render samples`: everything correct. The flat hour now shows a clean line with only the now dot.
16. `render mono samples`: correct.
17. `audit` at 360×640: 0 errors and 0 warnings. Info: deep nesting, and "4 variables never read".
18. `audit` at 320×160: same.
19. `inspect variables only_unused`: the "unused" ones are seg0..seg3. They ARE read (by graphicsLayer alpha) and the renders prove it, so this is a false positive. It also flags background/surface/track as unused.
20. `inspect accessibility` (hr=150): semantics present: "Heart rate 150 beats per minute, Cardio zone", "Active minutes, 34 of 60 min", "Calories, 1,460 of 2,200 kcal", plus the chart label. The chart's range was not announced, so I added a semantics description to the Min/Max text and to the widget chart.
21. `inspect runtime`: verdict idle ("never — nothing schedules a repaint"). Good.
22. `inspect bytes`: 32 KB. 33% is expressions; PathExpression and PathData come from the 8 LineChart expansions.
23. `convert check` (final): OK, with no findings except the host variables.
24. `render variants`: everything clean except "small" (the compact progress text was clipped) and "tiny" (180 wide, not supported).
25. `render variants`: after the shorter compact labels, everything was clean except "tiny".
26. `publish` (local, with variable_ranges): wrote `fitness.html`, a 1 MB playground.

## 2. Dead ends / wasted calls

- **Calls 13–14**: I declared `varied` above `hMin`/`hMax` in `resources.variables`. That was my fault, and the error message is clear. A `check` on a sample render would only have cost one call. A render with `samples` repeats the same conversion error once per sample instead of failing once.
- **Partly wasted: calls 7–8, the zone meter.** I assumed `step(x, e)` meant x >= e (GLSL-like). The build_kit snippets use step without saying it is strict (TIM-13: "k = step(@now, @t0) + ... counts the events already passed"). The definition only appears in `reference expressions`, which nothing in the workflow sends you to. If build_kit or the format reference said "step is strict (>)" once, I would have avoided this.
- **Call 9**: the 12 px overflow came from `spacedBy` in a row with a weighted child. The format reference does warn ("weighted children ignore spacedBy"), but the overflow finding doesn't name the cause. It just says "Size drawings from their box … collapsibleColumn … scroll", which sent me looking at the wrong things.
- **The flat-hour extremes**: the LineChart pitfall says "extremes (array mode) dots every value equal to the array's max or min". This is technically documented, but it never says that a flat series is therefore a solid bar of dots. My workaround was a second LineChart switched by visibility, which doubles the chart bytes.

## 3. Wrong, misleading, noisy or missing in the tools' output

- **Missing components in build_kit**: the kit returned no progress component even though "active minutes" and "calories" on a fitness dashboard are classic goal rings. It returned "calorie" as unmatched with no hint. It did not mention TextChoice, and it suggested the icons `fitness_center` and `dashboard`, but not `favorite` (heart), `directions_run` or `local_fire_department`.
- **STR-11 example**: build_kit offers STR-11, a canvas-only heart-rate sparkline with literal hex colours and hand-placed labels. That is the opposite of the kit's own design rules. It is labelled "take the technique", but it is noise for this goal.
- **LineChart `now` doc**: "Never a variable frozen at a value", and the pitfall "A chart of today's values: now is timeInMin()". For a chart in time relative to now (x_min −60, x_max 0), the right value is the literal 0. The guidance reads as if a fixed now were always wrong. Another line says "A literal 0 for now … counts as given", which helped.
- **step() strictness** is only in `reference expressions` (see above).
- **Audit false positives**: `unused_variables` reports variables read only by a `graphicsLayer` alpha modifier ("4 variable(s) are defined but never read") and reports them by id only. `inspect variables` additionally marks theme colours (background, surface, track) as unused although `consumed_by_ops` is non-empty.
- **Unclear finding paths**: paths like `statelayout[6].column[1]…` use an index (6) that does not match the 4 children I wrote, so it is hard to tell which layout a finding is in. Without the variant heading (call 7 output), there is no way to know.
- **Size warning advice**: the size warning (`at 360×384 … the content no longer fits`) recommends collapsibleColumn/fitBox/scroll. That is fine, but stateLayout on the window, which is what solved it here, only appears in the build_kit design rule, not in the warning.
- **Duplicate a11y reading**: inspect accessibility lists both my semantics node and the child texts ("150", "bpm", "Cardio"). Nothing says whether semantics on a parent merges or hides the children, so a screen reader probably reads the content twice. There was no guidance on how to merge.
- **publish**: the result's `variables` lists the floats but not `hrHour`, so the playground can't edit the array. `rc_bytes` (32,588) differs from convert's 32,570 without explanation.
- **Render file noise**: render with variants left stray `out/render-<timestamp>.png` files.

## 4. What I would have liked

- For goals with "X with a goal", build_kit should suggest ProgressRing/ProgressBar, and map calories/heart rate to icons.
- A one-line "expression semantics" cheat sheet in build_kit (step strict, ifElse argument order, a declare-before-use rule).
- LineChart: `extremes` should mark the first min and the first max only (or skip when flat), or there should be `argMin`/`argMax` functions so `marks` could be used. `label` should accept a text object, so the range could be spoken by the chart itself.
- For the overflow finding, name the likely cause when a weighted row also has spacedBy.
- Audit should show variable names and count modifier reads.
- A way to mark children as hidden from accessibility, or to merge them, when a parent carries a full description.
- A cheap documented "pulse" pattern (e.g. a scheduled repaint once per beat) or an explicit statement that any pulse costs a continuous repaint.

## 5. Honest assessment of the final screen

- **Content**: a big heart rate with a filled heart icon, and the zone name in the zone's theme colour (Rest = secondary, Fat burn = success, Cardio = warning, Peak = error) next to a 4-segment zone meter that lights up to the current zone. The last-hour LineChart has −60 min / −30 min / now labels, computed y-axis labels (rounded to 10 around min−5 … max+5), dots on the min and max, and a now dot. A header line reads "Min X · Max Y bpm". There are two ProgressRings (Active minutes, Calories) with value, "of goal unit", and "Goal reached" when the goal is met.
- **Host variables**: `hr`, `hrHour` (float array, 60 samples), `activeMin`, `activeGoal`, `kcal`, `kcalGoal`. Everything else (zone, min/max, axis range, progress, goal reached) is computed. All were verified at 58 (flat hour), 150 (spiky), 185 (rising) and at goals exceeded (95/60 min, 2650/2200 kcal).
- **Zones**: rest < 100 ≤ fat burn < 130 ≤ cardio < 160 ≤ peak. These are fixed thresholds I chose; they are not age-based (no age or max-HR host value).
- **Sizes**: a stateLayout on the window picks the layout. Widget (h < 300): hero, mini chart, and one row of mini rings. Short phone (h < 560): hero, chart, compact rings. Phone. Tablet (w ≥ 600 and h ≥ 560): side by side. These variants render clean: light, dark, mono, mono-inverted, narrow 259, wide, short, small, 4x2 320×160 and tablet. The tiny variant (180 wide) is not supported: the chart header and labels clip.
- **Themes and mono**: theme colours only. In mono the zone is readable from the name plus the count of filled segments, and the chart drops its wash.
- **Accessibility**: the document description is set. The heart rate and zone are spoken as one sentence ("Heart rate 150 beats per minute, Cardio zone"), the range as "Heart rate in the last hour ranged from 62 to 101 beats per minute", and each goal as "Active minutes, 34 of 60 min". Weak spot: the child texts are probably read as well (duplicates).
- **Repaint**: idle. There is no pulse animation: I chose a static heart because a pulse needs a running clock, and the reference says that repaints every frame.
- **Bytes**: 32.6 KB, which is heavy. The 4 layouts × 2 LineCharts (with and without extremes, for the flat hour) account for much of it. Dropping the flat-hour switch would save ~8 KB but leave a bar of dots on a flat hour.
- **Other weak spots**: when several samples tie for min or max, there is a dot on each. "now" is the last sample, not the clock (the host must push fresh samples). The tablet left column has empty space under the tiles. The rest colour (secondary = purple) is arbitrary.
